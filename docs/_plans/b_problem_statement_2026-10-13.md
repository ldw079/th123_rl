## 1. B 是什么, 为什么它卡住了

**B = 顶端标尺**: 真人(用户本人, 已裁定为固定测量员)与生产模型进行
BO15 系列对局(15 场先到 8 胜, 用户已裁定口径), 产出模型-人类比分,
使"超人"主张可判定; 同时复用产出教学闭环数据(习惯检测已有, 缺对局)。

**COM 标尺已论证饱和不可分辨**(F6 自知); 没有真人标尺, 整个项目的
一级目标(超人+教学)无法验收。这是当前全项目杠杆最高的一块缺口。

**卡点一句话**: 用户 2026-10-12 裁定"人测走**原版游戏**, D 盘特化版
专供训练"(B2' 改道)之后, **模型失去了进场通道** — 原版游戏没有 TCP
控制面, 而训练 mod 的锁步通道在人测实测中不可用(见 §2)。

## 2. 已走过的路(全部实测, 防规划智能体重踩)

### 2.1 失败路径: 训练 mod 直连(2026-10-12, 已裁定废弃)

- 做法: th123_train 游戏 + SOKUAI_P2_ONLY=1(mod 只覆写 P2 输入,
  P1 走物理键盘) + EvalEnv(render=True) + tps=60。
- 编译产物: SOKUAI_P2_ONLY 分支已随 MD5 1725B97C... 部署(血统合规,
  tools/mod_provenance.json 在案)。
- **实测症状**(三轮会话): ①窗口渲染混乱(用户两次报告只见标题画面;
  后经置顶截屏实拍到战斗画面 — 渲染本身在工作, 但用户体验层面不可
  用); ②**锁步帧率爬行 ~1fps**(内存探针: 血量/比分缓慢变化, 6 秒仅
  12 字节变化; py-spy: python 阻塞在 recv_frame 等游戏发帧); ③状态
  间歇冻结(暂停样形态)。
- 根因**未定位**(诊断中断于用户裁定改道; 已排除: mod boot 期渲染哑化
  — 部署 DLL 与源码 MD5 三方一致, 源码中启动哑化已注释; DISPLAY
  opcode 从未发送 off)。
- **结论**: 不推荐任何复用训练 mod 锁步循环的方案; 若某方案需要 mod
  侧改动, 必须走 C9 血统全流程(工具链 D:\vsc 就绪)。

### 2.2 存活路径: 原版采集(B2', 2026-10-12 已验证)

- `tools/human_solo_collect.py`: 启动原版整合包(无端口参数 →
  SokuAI 模组休眠不挂任何钩子, 用户日常手感) → 监视 replay 目录 →
  自动归档 → 会话末经 oracle 被动观测环境(D:\temp\rl_game,
  SOKUAI_OBSERVE=1, 离线重放)解算逐帧状态 → 习惯报告。
- **实测**: 用户 15 局 92,214 帧零错误入档; R79 审计后带有效性门/
  透明统计字段/distance-gated 检测器。
- 局限: 只能采集**真人单方**数据(打 COM/打本地 AI), 模型不在场 —
  这正是 B 缺的那一半。

## 3. 核心问题分解(规划智能体要解决的)

### P-B1: 模型的**观察通道**(它怎么知道局面)

原版游戏无 TCP/无共享内存接口。候选(不预设, 规划智能体评估):

- **(a) 纯 RPM 轮询**: 无任何注入, 对"原版"裁定最忠实。已知偏移覆盖
  scene/HP/score/位置/动作(见 §2.3); 但完整 CS 状态(灵力/手牌/对象
  列表=弹幕)的偏移链未全部核验, 轮询节拍与帧同步(60fps)的对齐方式
  未设计。风险: 偏移脆弱性(同 exe 内稳定, exe 更新即碎 — 可用 exe
  哈希断言守), 轮询 CPU 成本。
- **(b) 被动观测 mod 活化**: SokuAITrainerEnv 增加"活局观测"模式
  (不锁步/不控输入/不拉场景, 只逐帧 sendState)。**开放问题 Q1**:
  该 mod 现有形态是否依赖 rep 回放上下文, 活局(人打 VS COM/VS PLAYER)
  下能否稳定流式 — 未验证, 需 0.5 天探针。若可行, 状态保真度最高
  (与训练观测逐位同源), 但走 C9 血统(小改+重编+部署)。
- **(c) 画面输入**(摄像头/截图) — 项目已裁定暂缓(方案§6), 不在此列。

### P-B2: 模型的**行动通道**(它怎么出手)

- 人占键盘 P1 → 键盘注入(SendInput)会与人手冲突, **不可用**。
- **候选: 虚拟手柄**(vJoy/ViGEm 类): 游戏原生支持 P2 手柄键位
  (整合包含 ControlPnP/DPadFix 输入类 mod, 兼容性**未验证**)。
  模型侧 python 写 vJoy → 游戏 P2 键位绑手柄。需要: 驱动安装
  (用户已裁定: 工具可装, 装 D 盘), 键位映射表(与训练动作空间
  H/V/A/B/C/D/SW 的对齐), 帧节拍器(60fps 输出节奏)。
- **候选: mod 侧输入写入**(若走 P-B1-b 的 mod 路线, 顺手解决) —
  但那是回到"注入型 mod", 与"原版游戏"裁定的精神有张力, 需用户
  裁定可接受度。

### P-B3: **公平性口径**(读数可信的前提)

- 训练侧 tps=480, 人测天然 60fps — 无超速问题(游戏本身限速)。
- **模型反应延迟**: 已有用户裁定(2026-10-13, W1 语境): 80ms≈5 帧
  主档, 档位{0,3,5,8}。B 是否直接采用"观察延迟≥5帧"作为人测公平
  线?注意 W1 的延迟垫片(全管线口径)排在 B 之后 — 若 B 先行, 公平
  垫片需简化版(固定延迟读, 只垫观察不垫行动)。
- **信息遮蔽**(R11 红线在训练侧是 mod 做的): RPM/mod 观察会看到
  游戏内部全部真值(如极光实际天气) — 人测口径需显式声明哪些信息
  模型可见(建议: 与训练观测同构的遮蔽规则)。
- **模型快照固定**: 标尺对局必须锁版本(snap_ver 记档), rep+种子+
  快照三方可复现(复现性=标尺的可信度来源)。

### P-B4: **对局组织与测量协议**(B-2/B-3 既有草案, 待适配新架构)

- BO15 系列(15 场先到 8 胜, SeriesManager 语义已在, 需活局版 runner);
- 同尺锚定: 同一人类打 N 局 COM Lunatic(锚定刻度);
- 周度节律 30-60 分钟/次, 固定测量员=用户(已裁定);
- 每局游戏内存 rep(SaveRep)→ 自动进 human_solo 管线(模型侧数据
  同步归档); F6 战报增"vs Human"段(四口径报告可并列人类对位)。

### P-B5: **工程红线与共存约束**

- 特化版专供训练(裁定): 任何方案不得破坏训练侧现状; fleet 在跑时
  人测会话的 CPU 预算(红线 75%, 看门狗在役 — 但人测体验优先级应
  高于训练吞吐, 会话期间可考虑主动降 fleet, 停机走既有手动开关)。
- 公平红线(只写己方输入)/单写者/原子落盘全程有效。
- mod 改动(若有)=C9 血统全流程; 外部驱动安装=D 盘(裁定)。

### P-B6: **已知风险登记**(规划需逐条落缓解)

1. 训练 mod 锁步爬行根因未明(§2.1) — 任何间接依赖其代码路径的
   方案继承此风险;
2. vJoy 与整合包输入 mod 链(ControlPnP/DPadFix/giuroll)兼容性未知;
3. RPM 偏移脆弱性(exe 哈希守卫可测);
4. 人测会话与 fleet 的 CPU/体验争抢;
5. 被动观测 mod 活局形态未验证(Q1);
6. 用户手感干扰: 任何注入/轮询不得影响人类输入延迟与画面帧率。

## 4. 验收草案(规划智能体细化, 此为底线)

一次完整人测会话产出: ①用户 vs 模型 BO15 比分(逐场曲线); ②同尺
锚定局(COM Lunatic N 局); ③全部 rep 归档+模型快照版本+种子三方
可复现; ④F6 战报"vs Human"段落档。全程不违反 §3 红线; 训练侧
零感知(或仅有 CPU 预算内的吞吐波动)。
