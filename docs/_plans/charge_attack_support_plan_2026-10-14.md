# 蓄力攻击支持方案（CH-0..CH-5）— 2026-10-14

> 性质: 技法覆盖 L2 硬盲区修复方案（与"段位/近远A"盲区同级别）。
> 触发: 用户问询"模型和 rep 解析模块能正确分别普通攻击和蓄力攻击吗"——
> 答案为**三层面皆不能**（见 §1），本方案把该盲区转为可执行工作项。
> 格式: 遵循 PLANNING_AGENT.md 三段式（现状核验/可执行方案/验收途径）。
> 编号前缀 **CH-**（charge），避免与既有 A/B/E/F/I/K/S/W/V/P 冲突。
> 证据时点: 2026-10-14 下午，全部条目本轮亲验（grep/扫描/读源）。

## ① 现状核验

### 1.1 根因：游戏真值层无蓄力专属 Action ID

权威枚举表（`docs/soku_action_ids.md`，源自信锁 commit 09fed34 的 SokuLib
`Action.hpp`）**不含任何蓄力条目**：300=5A、400=5B……蓄力版与普通版共用
同一 Action ID。游戏内部以按键保持时长/pose/判定数据区分，不落在 action
字段。**一切从 action ID 派生的机制因此结构性失明**：

| 机制 | 位置 | 失明方式 |
|---|---|---|
| 动作 one-hot | feat_builder.py:425-427（`action//128` 粗桶） | 蓄力版同 ID 同桶，特征逐位相同 |
| 帧级事件 OPP_STARTUP | frame_events.py（触发条件 action∈300-598） | "蓄力 5A 要破防"与"普通 5A"触发同一事件 |
| 辅助预测头 8 类标签 | train_tm.py:1753（`min(action//128,7)`） | 同桶，预测头无法区分 |

### 1.2 观测侧：唯一候选信号 pose 从未做过真值验证

- mod 状态包**确实携带** `pose`/`poseFrame`（soku_client2.py:44 `CS_FIELDS`），
  特征 [304..307] 已入账（R57，含我方/对手各 pose+poseFrame）。
- 但 R57 测试（tests/test_guard_height.py）是**合成注入**（pose=0 vs 7），
  只验证"接线/生效"两道坎；第十轮批评的第三道坎"**正确**"（真实对局中
  玩家蓄力时 pose 确实变化、且足以区分）**从未验证**。round10 报告原文：
  "宣称的特性与实际生效的特性之间隔着接线/生效/正确三道坎"。
- 即便签名成立，pose/30 归一化标量也是弱信号（网络需自学语义）。

### 1.3 动作侧：宏动作空间对蓄力表达力为零

- 扫描全部 20 角色宏库（2026-10-14 脚本扫描）：**带按键的宏元组保持时长
  全部 <20 帧**；蓄力完成点按攻略口径 ≈30 帧量级（macros/suika.py:11 注释
  "B/JB: 发生17F(通常)/32F(蓄力)"）——帧数据知识在注释里，从未落成宏。
- 宏库只有普通版（如 `("5B", [(("B",), 10)])`）；纯按键宏连续重复选择在
  输入层理论上可延长按压，但属无定义行为（无标签/无奖励/无验收），且多数
  宏带方向预压帧会打断保持。**结论：模型永远使不出蓄力攻击。**

### 1.4 rep 解析 / BC 侧：信息在，语义无

- rep 输入流为逐帧原始 BattleKeys，**按压时长信息完整保留**（链路中唯一
  "能"的部分，信息论上可恢复）。
- `D:\temp\soku_arch` 解析模块**零蓄力相关代码**（grep 证实），无按压
  时长→蓄力的语义标注。
- StreamMatcher v3 把变长长按匹配到最长近似宏，低于阈值 0.85 整段丢弃
  （bc_match.py:117-126 注释即现场记录："实测 TR 语料 B 键按压率 6-30%
  而弹幕标签仅 1-2%"）——**专家蓄力行为被压扁成普通宏或整段丢失**。
- `tools/_diag_marisa_bullets.py` 统计过 >30 帧"长蓄"占比——诊断存在，
  **无后续修复跟进**。

### 1.5 已在位的使能件（本方案的可行性地基，均亲验）

| 使能件 | 位置 | 意义 |
|---|---|---|
| oracle 分片含完整状态+输入日志 | bc_build.py:131-146（`parse_frames`+`ilog`，CS_FIELDS 含 pose/poseFrame） | **CH-0 验证可全离线**跑在既有 ~750 双边分片上，无需启动游戏 |
| PPO 宏库扩展零初始化迁移 | ppo.py:231、277（旧宏数<新宏库时新宏零初始化，旧策略逐位保持） | **宏追加到列表尾 = 既有支持的迁移路径**，老检查点可加载 |
| learner 从 FeatureBuilder 派生 CORE_DIMS | F 系列 P0 修复后 | 特征维迁移不再是 fleet 死链风险 |
| CHM 攻略蓄力帧数据 | D:\touhou\...\③旧chm攻略-钢琴男（宏库同源管线 2026-09-21） | CH-2 逐角色提取的权威数据源 |
| 灵力参数已入执行器 | macro_executor.py:82（spirit） | 蓄力耗灵可后续接门控（本期仅文档化） |

### 1.6 缺口清单（本方案要补的）

1. 蓄力期/放出后的观测签名**未验证**（pose 是否可分）；
2. 逐角色**可蓄力招清单+蓄力帧阈值**未提取（20 角色全覆盖缺口）；
3. 宏库**无蓄力版宏**（动作空间表达力为零）；
4. BC 匹配器**无蓄力标签**（专家数据系统性丢弃）；
5. 特征/事件层**无"对手蓄力中"信号**（预警盲区）。

## ② 可执行方案（CH-0..CH-5）

### CH-0 蓄力语义探针（离线，0.5 天）— **全方案的门**

在既有 oracle 双边分片（`data/oracle_v2/shards/tr*.npz`）上离线统计：

1. 从 `ilog`（mod 输入日志，与状态帧同帧 1:1）找**同键连续按压 ≥25 帧**
   的窗口（双侧、全角色）；
2. 对每个窗口提取该侧 `(action, pose, poseFrame)` 逐帧轨迹，产出：
   - **Q1 蓄力期签名**：按压期间 pose/poseFrame 是否呈现稳定模式
     （区别于待机/普通出招/移动）？签名是全局的还是逐角色？
   - **Q2 放出后可分性**：松键后打出的招，action ID 是否与普通版相同
     （验证枚举推定）？pose/poseFrame 轨迹是否可区分蓄力版与普通版？
   - **Q3 阈值分布**：按压时长→实际出招形态的边界（二值还是有中间档，
     弹幕系是否连续蓄力等级）。
3. 产出物：`docs/_reviews/charge_semantics_probe_2026-10-XX.md` +
   签名查表数据（供 CH-1 实现为 FeatureBuilder 查表位，同 LOW_ATTACK_IDS
   模式）。

**门规则**：若 Q1 无可用签名（pose 在蓄力期与普通状态不可分），观测侧
（CH-1 特征位）**不施工**——不为不存在的信号造特征（R11 数据纪律精神），
盲区如实写入可行性文档；动作侧（CH-2/3/4）不受影响照常推进。

### CH-1 观测特征 +2 维（0.5 天，并窗 S-2 迁移）

- 新增 2 维（对手侧）：`opp_charging`（CH-0 签名的在线判定位，查表实现）
  + `opp_charge_len/60`（蓄力已持续时长归一化——蓄力越深威胁越大，
  且给"快满蓄力时打断"的反应学习提供梯度）。
- **迁移协调**：S-2（合并方案）的 CORE_DIMS 330→342 若尚未施工 → 改为
  330→**344** 一次迁移；若已施工 → 单独 +2 迁移，同纪律（段位账本 assert
  + test_feat_segments 更新 + learner 派生自动跟随）。
- 可选二期（不阻塞验收）：frame_events 新增 `E_OPP_CHARGE` 事件
  （反应规则候选：插动/DD 惩罚/后撤，帧窗值从攻略提取），复用既有
  事件→掩码→策略决策路径。

### CH-2 蓄力帧数据提取（0.5-1 天）

**数据源升级（2026-10-14 补，用户裁定权威源）**：用户指认并裁定
`https://soku.cleista.cc/framedata` 为**权威帧数据来源**（已入宪 R4
来源清单=R111）——全 20 角色帧数据库，**蓄力版独立成行**
（`?charged=1` 参数区分）。
萃香抽查实测：5[B] 蓄力发生 30f（普通 5B 15f）、2[B] 36f、6[A] 33f、
3[A] 34f、f.5[A] 35f、236[B] 128f——**逐招蓄力帧数可直接导入**。
CHM 文本提取降为交叉验证源；R105 登记的三主力 `extrapolated_from_suika`
外推值（攻略无系统蓄力表）在站数据导入后**整体替换**；与 hitlab 实测
出入并列上报用户裁定。下表产出物以站数据为 `source="cleista"` 主源。

从数据源（站为主、CHM gb18030 交叉验证）逐角色提取：

- 可蓄力招清单（B/C 弹幕蓄力角色 + A 蓄力角色如妖梦/美铃系）；
- 每招蓄力完成点帧数（宏保持时长 = 完成点 + 4 帧余量）；
- 蓄力灵力成本（文档化，本期不做执行器门控）。

产出物：`macros/charge_table.json`（逐招：角色/招式/阈值帧/耗灵/攻略出处）。
**数据纪律**：20 角色全覆盖——攻略未提供的角色显式标 `"source": null`，
**不编造帧数**（同 rep_meta.py 的 source 标注原则）。三主力角色
（suika/marisa/reimu）优先——suika/marisa 的蓄力帧已有注释级证据。

### CH-3 蓄力宏入账（1 天）

- 每角色宏列表**尾部追加**蓄力版宏（保序 = 索引稳定 = ppo.py:231 零初始化
  迁移直接适用）。命名 `"5B蓄"`/`"2B蓄"`/`"6C蓄"`（中文后缀与库风格一致）。
- 时间线形态：方向预压（如有）+ 按键保持 = CH-2 阈值帧（如萃香 5B蓄 ≈
  `(("B",), 36)`）。
- 执行器语义（均已在位，无需改动）：受击中止（d_take>80 清队）与 R34
  对手近距攻击清队对蓄力宏同样生效——**蓄力是承诺性动作，被打断是正确
  行为**，这正是模型要学的风险判断。
- **兼容验证点**：league/eval 旧快照在新宏库下加载（走零初始化迁移，
  旧策略逐位不变）——补一个加载等价测试钉死。
- 门禁/自检：gate_selftest 与 contract_check 若硬编码宏数量需同步
  （以派生值为准，不硬编码）。

### CH-4 BC 蓄力标注（1 天）

- 词汇表加入蓄力宏后 StreamMatcher 自动获得匹配目标（长按段 vs 蓄力宏
  时间线相似度高）。
- **反退化测试**（本组件核心验收）：合成按压 8 帧→标 `5B`、35 帧→标
  `5B蓄`、20 帧（阈下）→标 `5B` 且不得被"更长最优"偏好误吞为蓄力前缀。
- 复跑 `tools/_diag_marisa_bullets.py`：弹幕标签占比应从 1-2% 向按压率
  下限方向**实质收敛**（6-30% 与 1-2% 的缺口即被丢弃的长按）。
- 与 S-5（专家后处理）的接口：蓄力标签行同样进入 S-1 MyPunishTracker 的
  "招式类别"分类——CH 方案把"蓄力弹"登记为一个类别即可，无结构改动。

### CH-5 训练接入与观测（0.5 天 + 2 周观察）

- **不改奖励**：蓄力攻击的高伤害自然经 d_deal 流入回报——刻意零奖励改动
  以**保护 A1-2 被动性 A/B 的干净性**（该实验在观察期）。
- F6 战报新增蓄力统计段：蓄力宏使用率/使用-胜负相关/对手蓄力窗口内
  我方防御与插动率（CH-1 位生效后）。
- 观察不设硬指标门槛（涌现性学习），但**必须有数据**：两周后战报若
  蓄力使用率恒为 0，登记为学习动力学问题转 S-9' 同批裁定（是否加诱导），
  而非静默搁置。

## ③ 验收途径

### 逐组件验收（全部可自动化或可复现）

| 组件 | 验收 | 判据 |
|---|---|---|
| CH-0 | 探针报告 | Q1/Q2/Q3 有定量答案：签名窗口样本 ≥N（跨 ≥M 分片/≥K 角色），签名判定准确率 ≥90%（蓄力窗口 vs 普通窗口的分类）；无签名则显式记录"观测侧盲区成立" |
| CH-1 | 行为测试（R57 模板升级版） | 合成注入：蓄力态→位翻转；**真值回放**：在 CH-0 标注窗口上离线重算特征，位在 ≥90% 蓄力帧为 1、普通攻击帧误报 ≤5%；段位账本 assert 到 344 |
| CH-2 | 数据表审计 | 20 角色全覆盖；每条帧值带攻略出处标注；**零编造**（source=null 的角色单独列出） |
| CH-3 | 三层测试 | ①执行器单测：蓄力宏产出 N 连续同键帧；②迁移等价测试：旧检查点新宏库加载后旧宏 logits 逐位不变；③实机冒烟：side_driver 一局，蓄力招真实放出（状态流中观察到蓄力形态） |
| CH-4 | 匹配器单测+诊断复跑 | 8f/20f/35f 三档标注正确（反退化）；diag 复跑弹幕标签缺口实质收敛；BC 蓄力标签行数 >0 |
| CH-5 | 两周 F6 战报 | 蓄力统计段有数据；使用率>0（=0 则登记转 S-9' 裁定，不静默） |

### 总体验收（闭环判据）

**"能分别普通攻击和蓄力攻击"在三个层面各自成立**：
1. 观测：对手蓄力中/蓄力放出，特征层可分（CH-0 签名 + CH-1 位，真值回放
   验证）；若 Q1 无签名，则该层以"已论证的结构性盲区"结案（action ID
   同源，游戏真值不提供区分信号）；
2. 动作：模型可执行蓄力攻击（CH-3，实机冒烟验证）；
3. 数据：专家蓄力行为进入 BC 语料（CH-4，标签占比收敛验证）。

### 红线自检

- 不改奖励（保护 A/B）；不改 mod（零 C9 触发）；特征只加不改既有位
  （段位账本纪律）；数据零编造（CH-2 source 标注）；旧快照兼容有测试
  钉死（league/eval 不静默失效）。
