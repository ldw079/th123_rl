# Part 1 感知层：pose/变体/段位（前置项）

## 1.1 问题：三盲区同根一处死代码

| 盲区 | 根因 | 证据 |
|---|---|---|
| 近A(300)/遠A(301) 不可分 | 动作 one-hot `//128` 八桶, 300/301 同桶 2 | feat_builder.py:329 |
| R49"细分标记"无效 | 门控 `128≤action<256` 是受击段不含攻击区; 且 `(a//64)%2` 对 300/301 同为 4→0, 数学上分不开 | feat_builder.py:332-339（第十八轮 §2.5） |
| **pose/poseFrame 是死变量** | 四变量计算后从未写入任何维度（注释称写入段3空闲位, 实际只写 back_turned 与 0.0） | feat_builder.py:317-320 → 342-345 |
| 段位/蓄力不可见 | 同上: pose 才是变体/蓄力的权威信号; 下段属性无任何特征位 | 攻略防御篇逐角色段位表无法被模型消费 |

## 1.2 方案：CORE_DIMS 308→316（+8 维, 走成熟迁移）

**为什么扩维而非挤死维**: 308 维现已填满（段宽和恰为 308; 段 11 的 [o+11..o+21] 已被 R51 池序占 11-19, 仅剩 2 格不够用）。项目有 260→308 扩维迁移的完整先例（零初始化迁移 + repad 工具 + 迁移断言）。

**新 8 维定义（追加在 core 尾部 308-315）**:

| 维 | 内容 | 归一 | 用途 |
|---|---|---|---|
| own_pose | left.pose | /32 | 自家动作变体编号（近/远版、蓄力版） |
| own_poseFrame | left.poseFrame | min(1, /32) | 变体内进度（蓄力时长可读） |
| opp_pose | right.pose | /32 | **对手近/遠A、蓄力状态**——段位与确反判断的输入 |
| opp_poseFrame | right.poseFrame | min(1, /32) | 对手蓄力进度（"看到蓄力就蹲防"的攻略条件） |
| own_fvariant | action ∈ {301,311,321,331,…}(f 变体集) | 0/1 | 自家近/远版显式位 |
| opp_fvariant | 对手侧同上 | 0/1 | 对手遠A 警戒（帧数据不同的那批） |
| opp_low | 对手 action ∈ 下段表 | 0/1 | 段位感知——中下择防御的输入 |
| opp_charge | 对手 pose ∈ 蓄力变体集 | 0/1 | 蓄力择（H6A/H3A 爆灵）预警 |

**数据源纪律（R4"不猜数据"）**:
- f 变体集: SokuLib 枚举的既定规律（`5A:(300,301)/2A:(303,311)` 已在 reach_maps 权威登记）——工具生成, 人工核对三角色;
- 下段表: 从解包 XML 的 hitbox 位置 + 攻略防御篇"下段标注"交叉——**先在 reimu 一角色落地验证**, hitlab 复核后才扩全角色（空表优于错表）;
- 蓄力 pose 集: XML 动作变体注释（"蓄力"标注）——同上, 先验一角色。

**接线与同步面**:
- feat_builder.build() 写入 → train_tm/side_driver/bc_build **自动同源获得**（三方都走 fb.build）;
- ppo.py 迁移: `_CORE_DIMS` 断言 308→316, `_map_row` 尾段映射（core 常量段平移, 已有机制）; OPP_CORE_OFF 152→160（对手段起点后移 8）——**ppo_gpu 的 OPP_CORE_OFF 同步改**（等价性测试会抓漂移）;
- BC 库 repad +8 零列（repad 脚本更新布局版本号 '5N+316:v3', 旧版拒跑）;
- 现存模型零初始化迁移（新 8 维零列 = 旧策略逐位不变——项目标准迁移语义）。

**门禁（行为断言, 替换 R49 的子串断言）**:
1. 构造 left.pose=5 vs 15 的两帧 → own_pose 维必须差 10/32;
2. 构造 action=301 → own_fvariant=1（action=300 → 0）;
3. 下段表非空的 action → opp_low=1;
4. 配对变异 ×3（删写入/错桶/错偏移各一）。

**工作量**: 特征+迁移 ~半天; 三方验证+门禁 ~半天; 下段/蓄力表数据核验 1-2 天（可后置, 先空表上线 pose 四维+fvariant 两维）。

## 1.3 分步上线路径（降低一次性风险）

- **P1-a（先上 6 维）**: pose×4 + fvariant×2 —— 零数据核验依赖（SokuLib 枚举即权威）;
- **P1-b（后补 2 维）**: opp_low/opp_charge —— 等 reimu 下段表 hitlab 复核。

## 2.3 中期：门系统升级——分支压制树（攻略 2B 压制树的工程化）

**核心改动: 门从"二值截断"升级为"分支路由"**。攻略已给出完整决策树（2B 后按对手行为六分支: 小跳→C / 大跳→J6A / 2DD→J6A / 抢A→C / 凹→无缝妖怪 / 回灵→远A——日WIKI+钢琴男压制章）, 当前架构只有 hit/blocked 两叶。

**宏脚本语法扩展（向后兼容）**:
```python
# 现行: ("confirm", 0)
# 扩展: ("branch", {"hit":    [后续步...],
#                   "blocked": [...],          # cconfirm 语义
#                   "whiff":   None,           # 截断=现行为
#                   "opp_jump": [...],          # 对手 airBorne 变真
#                   "opp_dd":  [...],           # 对手 action∈结界段(150-167→脱离)
#                   "delay_then": (3, [...])})  # 放帧: 门通过后延迟N帧再续
```
- **放帧（stagger）以门参数实现**——修正第十七轮 frame_macros 的概念错位（独立宏不构成拍子择; 延迟必须相对上一招的打防结束）: `"AA 放帧 A"` = A + branch(hit → delay 3 → A);
- **拍子择的动作空间表达**: 同一连段的 快/慢 两个宏变体（生成器从 branch delay 派生成对宏）——保持平坦 softmax, 策略层选择节奏;
- **实现位置与防漂移**: 门推进逻辑在 train_tm:981-995 与 side_driver 同步存在（双拷贝!）——**本次必须借 episode_core 的组合复用模式统一执行器**（连段步进器抽为共享模块, train_tm 与 side_driver 共同引用; fleet 的 actor 自动继承）——这是宏执行器统一的最佳时机;
- 观察窗条件的数据源: opp_jump=airBorne 沿; opp_dd=GUARD 段进入后离开沿（frame_events 的 E_GUARDSTUN_END 已有）; opp_attack=E_OPP_STARTUP 沿——**frame_events 与门系统在此合流**（同一事件源两处消费）。

**门禁**: 分支全路径合成帧测试（test_smoke_driver_r38 模式: 每分支一用例）; 变异: 删一分支路由必须红。

## 2.4 远期：目押自适应（依赖 Part 1）

固定帧 → 条件帧: 连段步进器读 `对手 hitstun 剩余`（untech 字段每帧可见）, 下一击条件改为"对手 hitstun 结束后 ≤2 帧内"而非固定第 N 帧——**把 2.3 的 branch 门与 untech 感知组合**: `"link": (max_wait, steps)` = 等待 untech→0 后最速出招, 超时 max_wait 落空截断。近/远A 分辨（Part 1 的 fvariant）在此必需——遠A 起手的取消窗口与近A 不同, 步进器按 fvariant 查两张帧表（MOVE_STARTUP 已有基础, 需扩 f 变体列）。

## 2.5 可选：ender 菜单（宪法既有制度, 触发条件已到）

宪法 SOP 第 10 步: "宏数>60→分层连段架构(ender 菜单)"——三现役 63/69/70 已越线。设计: 起手宏 + ender 宏两段式（起手 confirm 通过后, 策略在 ender 菜单中二次选择——按 LIMIT/comboDamage/spirit/版距特征条件化）。收益: 连段数不膨胀而路由空间扩大; 成本: 决策点增加一次（连段中途的二次决策需要快路径）。**列为可选项**: 先做 2.3/2.4, ender 菜单在宏数再次触顶时启动。
