## 1. 方案主体——两条并行线

### 线 A · confirm→branch 宏库升级（宏库改造, 3 天）

**原则**: 把现有 12 个含 confirm/cconfirm 的宏升级为 branch 门版本——**同一宏名**（零训练面变化, 掩码/计数/类别集合不变）, 脚本内部从"二值截断"改为"多路路由"。

#### A-1 升级模式（以"压制A"为例）

**现行**（二值截断）:
```python
("压制A", [
    (("down",), 6), (("down","A"), 8), ((), 3), ("cconfirm", 0),
    (("right","A"), 10), ((), 3),          # 门过后固定接 6A
    (("down","B"), 10), ((), 3),           # 接 2B
    ...
])
```

**升级后**（分支路由）:
```python
("压制A", [
    (("down",), 6), (("down","A"), 8), ((), 3), ("branch", {
        "hit":    [("confirm_ok", 0)] + _COMBO_TAIL,   # 命中→连段收尾
        "blocked": [("confirm_ok", 0)] + _PRESSURE_TAIL, # 被防→换压制
        "opp_jump": [("confirm_ok", 0)] + _ANTI_AIR,     # 对手跳→对空
        "whiff":   None,                                  # 空挥→截断(同现行为)
    }),
])
```

branch 的四路含义与攻略对齐（压制树工程化）:
| 分支 | 语义 | 攻略依据 |
|---|---|---|
| `"hit"` | d_deal>0（命中）→ 连段路由 | confirm 门升级版 |
| `"blocked"` | 对手在防御态（GUARD_STUN_IDS）→ 压制变奏 | cconfirm 门升级版 |
| `"opp_jump"` | 对手 airBorne → 对空/追打 | 新增（攻略空压转下地 3 择） |
| `"whiff"` | None → 截断 | 同现行为（空挥交还决策权） |

#### A-2 12 个宏的升级策略

| 宏 | 现行门 | 升级重点 |
|---|---|---|
| 5A确认 / 2A确认 / 原子·确认5A | confirm | hit→连段尾; blocked→压制接续; opp_jump→对空 |
| 连段A/B/C | confirm（中部） | hit→继续连段; blocked→换弹幕压制; opp_jump→追打 |
| 压制A/B | cconfirm | hit→连段转换; blocked→压制变奏; opp_jump→对空 |
| 空连A | cconfirm | hit→空中连段; blocked→空防; opp_jump→空对空 |
| 版边连A | confirm | hit→版边连全出; blocked→磨灵循环; opp_jump→对空 |
| TM·2a/4a连 | confirm | hit→连段全出; blocked→截断; opp_jump→对空 |

**注意**: 分支的后续步列表**不新增宏名**——它们是脚本内嵌步骤, 不进动作空间/掩码/计数。策略层零变化。

#### A-3 工作量拆分

| 步 | 内容 | 工作量 |
|---|---|---|
| A-3.1 | branch 脚本编写器（`macros_branch.py`, 函数式生成 branch dict, 12 宏共用模板） | 0.5 天 |
| A-3.2 | 12 宏逐个升级（每宏设计 2-3 条分支后续, 攻略查证对空/压制变奏的输入序列） | 1.5 天 |
| A-3.3 | 行为测试（每宏 4 条分支路各 1 测试 = 48 条, 合成帧驱动执行器） | 0.5 天 |
| A-3.4 | 门禁断言 + 变异（branch 门存在性/四路可达性/无幽灵步） | 0.5 天 |

#### A-4 验收

- 12 宏全部含 branch 步; 行为测试 48/48（四路各覆盖）;
- `confirm/cconfirm` 仍保留（未升级宏继续使用, 向后兼容）;
- 训练侧零变化: 掩码不变/计数不变/动作空间不变——只是宏内行为更智能;
- 30 分钟冒烟对局: 压制宏被防后出现变奏（不再是固定后续）。

### 线 B · 帧级事件系统补强（新增 2 事件 + 既有完备化, 1 天）

#### B-1 新增事件: OPP_GUARD（对手进入防御态）

**用途**: 我方压制宏执行中, 对手开始防御 → 策略可选择换弹幕磨灵/换择/撤退——当前此信息仅在 cconfirm 门里以"被防了"间接感知, 事件级触发让策略更早介入。

```
检测沿: opp_a 进入 GUARD_STUN_IDS(150-166除158) 且 last_opp_a 不在
窗口: 8 帧
掩码候选: 弹幕系(5B/2B/5C)、体术换择(6A/3A)、后退、结界
```

**工作量**: 检测沿 0.5h + 掩码 0.5h + 测试/门禁 1h = **0.5 天**

#### B-2 新增事件: COMBO_DROP（连段中断）

**用途**: 我方连段宏执行中, 对手 untech 从 >0 变 0 且我方未在攻击态 → 连段确认失败（对手恢复） → 策略选择收招/撤防/压制重入。

```
检测沿: right.untech 从 >0 变 0 且 my_a < 100（非攻击中）
窗口: 6 帧
掩码候选: 后退/立防/前冲/弹幕（连段失败后的攻防选择）
```

**工作量**: 同上 **0.5 天**

#### B-3 既有 6 事件的掩码完备化审查

当前 reaction_mask 是前缀匹配（曾出过 `2A→2A确认` 误解析已修）; 逐一审查 6 种事件的掩码是否包含攻略推荐的全部选项——预期发现 2-3 个遗漏（如 GUARDSTUN 的掩码可能缺结界选项）。

**工作量**: 审查 0.5h + 补充掩码条目 0.5h = **0.5 天**

## 3. 风险表

| 风险 | 概率 | 缓解 |
|---|---|---|
| branch 路由在某场景下不如 confirm 直觉（策略没学过新行为） | 高（初期必然） | 分支后续步选**攻略推荐的标准答案**（非创新行为）, 本质是"更智能的硬编码"而非"需要学习的新策略"——初期即应优于 confirm |
| 12 宏同时升级引入宏库级 bug | 中 | 逐宏升级逐宏测试（A-3.3 每宏 4 测）; 可分两批（先 6 压制系后 6 连段系）|
| branch 的 opp_jump 分支在对手短暂跳跃时误触发 | 中 | airBorne 检测加最短持续帧（如 ≥3 帧才认定跳, 非单帧弹跳）|
| 事件增多导致决策频率过高（训练数据碎片化） | 低 | 事件有冷却窗（2×窗口帧）; 实测事件频率仪表已有 |
| 训练中宏行为变化导致分布漂移 | 中 | 宏名不变 → 掩码/探索配额/BC 锚不变; 但宏内行为不同 → PPO 的 on-policy 假设仍成立（行为策略=采样策略, 同一帧） |
