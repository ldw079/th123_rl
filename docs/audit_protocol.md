# 审计制度(用户 2026-10-12 指令固化)

> **地位(2026-10-12 用户令)**: 本文件是**审计智能体的唯一入口路由**, 地位与
> `AGENTS.md` 之于开发智能体同级 — 审计接手第一读。开发路由见 `AGENTS.md`,
> 规划宪章见 `PLANNING_AGENT.md`; 规范冲突时以 `METHODOLOGY.md`(宪法)红线为准。
> 三条必要条件为用户明令,违反即审计无效。细则为操作化展开。
> 配套归档目录: `docs/audit/`(审计结论按时间归档)· `docs/bugs/`(bug 档案,
> 见 `docs/bugs/bug_protocol.md` — 审计挖出 bug 时立档)。

## 一、三条必要条件(用户明令)

### 条件1: 只读最新状态,不复审旧代码

- 每次审计**必须先锚定基线**: `git log --oneline -1` + `git status --short`,
  报告开头记录"基线 commit + 审计时刻时间戳"。无基线锚的审计无效。
- 审计范围 = 基线 commit 的工作区现状(含未提交改动 — 未提交改动是
  "新代码"的第一嫌疑对象,不是豁免区)。
- 已归档的旧审计结论(`docs/audit/` 历史档)只作历史对照,**不得**作为
  "某段代码已审过"的免审凭证;旧档覆盖的代码若在本次基线中已被改过,
  照审。
- 运行时状态类字段一律带时间戳读取与记录(2.64 教训:"训练运行中"
  不带时间戳 = 3 天后即成误导)。进程数/日志 mtime/产物 mtime 同刻
  采样,注明采样时刻。

### 条件2: 结论整理为文档并按时间归档

- 每次审计产出一份报告: `docs/audit/audit_YYYY-MM-DD_<scope>.md`
  (scope 短横线英文, 如 `code_health` / `commits_<sha>_<sha>`)。
- 报告必含五要素:
  1. 基线(commit + 工作区状态)与审计时刻
  2. 范围与方法(跑了哪些门禁/工具/读了哪些日志)
  3. 结论(明确判定: 正常/异常/待观察)
  4. 遗留项与建议(带优先级,注明"待用户指令"与否)
  5. 与上一次归档审计的差异摘要(一句话即可)
- 审计期间**只读不修**(审计与修复分离;发现问题的交付物是报告,
  修不修、怎么修由用户指令)。审计触发的临时探针命令不得留残档。

### 条件3: 数轮大更新后全面从零审查

- 触发条件(满足其一即应建议用户安排从零审查):
  - 距上次从零审查累计 ≥5 个版本波次(METHODOLOGY 修订记录计数);
  - 单波改动 >1000 行且触及训练语义(奖励/宏/门控/更新器);
  - 发生维度类变更落地(CORE_DIMS / EP_SCHEMA / 宏数)之后的首次窗口;
  - 从零审查发现过 P0 级问题的,修复后下一轮加验一次。
- 从零审查 = **不依赖任何先前审计结论**,全库重验: 门禁全量 + 变异
  自检抽查 + 模块 import 图 + 产物/日志/进程三面对账 + 文档与实盘
  对账(参照 `docs/_reviews/full_review_from_zero_2_2026-10-06.md` 体例,报告同样
  归档入 `docs/audit/` 并在标题标注"从零")。

## 二、标准审计清单(每次至少跑齐前四项)

| # | 项 | 命令/方法 | 备注 |
|---|---|---|---|
| 1 | 基线锚定 | `git log -1` + `git status` | 报告头记录 |
| 2 | 契约门禁 | `tools/contract_check.py` | 实测数字,不信文档记载 |
| 3 | 全量审计工具 | `tools/audit_all.py` | 注意其日志尾读会跨代际混读,异常行需回原日志定界甄别(已知弱点) |
| 4 | 运行时三面对账 | 进程(CIM)/日志 mtime/产物 mtime | 状态带时间戳;深夜集体消失无停机记录=疑似外部终止,如实记录停因未知 |
| 5 | 日志异常甄别 | 回原日志,以"最近一次初始化"为界 | 旧代际异常不摊到现行代码头上 |
| 6 | 新增代码审查 | 按 `git diff <上次审计基线>..HEAD` | 有新增波次时必做 |
| 7 | 实盘读数 | league/评估矩阵/仪表曲线 | 与门禁数字相互印证 |
