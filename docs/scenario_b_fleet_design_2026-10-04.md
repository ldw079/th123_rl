# 场景 B 详细设计：单机多环境 + 批式中央 Learner（车队 Fleet 架构）

> 日期: 2026-10-04 · 状态: 设计稿（待实施）
> 目标: 在单台云 GPU 主机上把训练吞吐从 ~190 万决策/天提升至 **1.5-2.5 亿决策/天（6-12 倍）**，同时不牺牲学习质量（三条红线的机制化落实）
> 依据: 现有代码逐行审查（十七轮）+ 实测基线 + PPO 分布式实践惯例
> 姊妹文档: goal_feasibility（天花板1/5）· 第十七轮严审（ppo_gpu 残留）· 模型体检

---

## 0. 设计原则（先于一切）

1. **纯放大，不换算法**：奖励/宏库/frame_events 规则层/退火日程/BC 管线全部不动——车队只是把"每局串行更新"换成"N 环境并行采集+攒批更新"，PPO 语义经三条红线保持。
2. **单写者纪律不破坏**：每角色仍只有一个 learner 写自己的模型档；对手池/宏计数/蒸馏数据各有唯一属主。
3. **模型格式双向兼容**：numpy 与 GPU 版互读是硬前提（现状单向，见 §8 前置 F2）。
4. **治理随行**：每条新机制配门禁断言+配对变异；fleet 的端口/同步/独立性各有行为测试。
5. **每步可回滚**：fleet 产物与现行单实例产物完全同格式——关掉 fleet 立即退回现行 trainer。

## 1. 基线与瓶颈（实测）

| 项 | 现状 | fleet 目标 |
|---|---|---|
| 游戏实例 | 3（三角色各一） | 8-16（按 league 分配） |
| 局速率 | ~69 局/h 合计 | 500-1000 局/h |
| 决策量 | ~8.1 万/h（190 万/天） | 60-110 万/h |
| 更新 | 每局一次（~1k 样本, numpy, 40-80s, 局首 join 串行） | 每批 K 局（4-8k 样本, GPU, 2-5s） |
| 单局墙钟 | ~160s（战斗 31-60s + 更新等待 40-80s + 轮换 boot 20-40s） | ~50-70s（去更新等待） |

## 2. 总体架构

```
┌──────────────────────────── 单台云主机（Windows, A10 GPU, 32-64 vCPU）────────────────────────────┐
│                                                                                                  │
│  actor_worker ×N（独立进程, 每个含 1 游戏实例）                                                    │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐          ┌──────────┐                                  │
│  │ actor#0  │  │ actor#1  │  │ actor#2  │   ...    │ actor#N-1│                                  │
│  │ reimu    │  │ reimu    │  │ marisa   │          │ (league) │                                  │
│  │ th123.exe│  │ th123.exe│  │ th123.exe│          │          │                                  │
│  │ 采样快照  │  │ 采样快照  │  │ 采样快照 │          │          │                                  │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘          └────┬─────┘                                  │
│       │episode.npz(+logp)             │                   │      §4 经验道（原子落盘+版本戳）        │
│       ▼                                ▼                   ▼                                        │
│  ┌──────────────────────────────────────────────────────────────┐   §5 中央 learner（每角色一个）      │
│  │ learner_hub: 摸批(K局/超时) → ppo_gpu.update(存入式logp_old)   │                                      │
│  │   → save(numpy双向格式) → 快照发布(版本号) → 池快照/蒸馏/宏计数 │                                      │
│  └──────────────────────────────────────────────────────────────┘                                     │
│       ▲ 快照刷新（局边界, 版本轮询）                                                                    │
│  supervisor（fleet 监督: 死亡重启/错峰 boot/健康仪表）                                                 │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

**进程模型选择的依据**: 每帧 Python 处理（track_bullets/奖励/特征）在 436fps 下单环境即占 ~40-80% 核——**多线程会被 GIL 串死，必须多进程**（沿用 run_parallel 的子进程习惯）。learner 独立进程持有 GPU；actor 用 numpy 推理（单样本前向 numpy 快于 torch-CPU 的调用开销）。

## 3. 组件设计

### 3.1 actor_worker.py（新；从 train_tm 抽取共享库）

**关键: 不复制粘贴 episode 循环**（macros/side_driver 双拷贝漂移是本项目最大事故源）。把 `TMTrainer._run_episode` 的核心（帧循环+奖励+决策+frame_events+deck）抽成 `episode_core.py` 的纯函数/上下文对象，actor 与现行 train_tm **共同引用**。

每 actor 职责:
- 1 个 `TMEnv`（含游戏进程），端口取自 fleet 车道（§3.4）;
- 局边界从快照目录**原子加载**当前版本采样快照（numpy ppo 前向推理，`_ppo_act` 语义不变）;
- **采样时记录 logP(a)**（sample 已算出 P，顺手存对数——红线①）;
- 每局产出 `ep_{char}_{actor}_{ts}.npz`: feats(uint8)/sides/acts/rews/masks/bc_targets/logp/opp_next + meta（rng 种子、快照版本、对手标签、deck）——**原子写**（tmp+rename，项目惯例）;
- 独立 rng（种子=(actor_id, episode_idx) 派生——红线③）、独立 deck 采样、独立对手轮换;
- 上报: 宏计数增量、[matchup] 战绩、帧级事件计数（learner 汇总）。

### 3.2 learner_hub.py（新；每角色一个进程）

- **摸批策略**: 缓冲区 ≥K 局 或 距上次更新 >60s 即触发（K 默认 4，上限 8——§6 陈旧度论证）;
- 更新: `ppo_gpu.update(..., logp_old=stored)`（**新参数**——红线①的 learner 侧；replay 行的 R38 机制即此先例）;
- 保存: numpy 双向格式（§8-F2 修复后）; **快照发布**: 写 `snap_{char}/v{n}.npz` + 原子递增 `version` 文件;
- 保留现职: 池快照（每 50 局聚合 actor 战绩）、蒸馏数据合并、BC 库加载、meta 退火（退火按**更新次数**走，样本量放大自然缩放）;
- 仪表: 陈旧度（批内最大版本滞后）、更新/小时、批样本数、|KL|/熵/值损（沿用 [ep] 行格式）。

### 3.3 同步协议（红线②的机制化）

```
actor 主循环:                       learner 主循环:
  版本 = read(version文件)            收集缓冲
  快照 = load(v{版本})                ≥K局 或 超时 → update(存入式logp)
  跑一整局(策略冻结=快照)              save + 发布 v{n+1}(原子)
  写 episode.npz(带版本戳)            循环
  循环
```

- 快照只在**局边界**加载——与现行 `_ppo_act` 每局冻结语义**完全一致**;
- 局跨更新边界时（开局于 v_n、收局时已是 v_{n+1}）: logp 按 v_n 记录，ratio=π_{n+1}/π_n 由 PPO clip 正确处理——这正是重要性比的本职（论证: 每更新 KL~0.03-0.06 → 陈旧 1-2 次更新的 ratio≈e^0.1~1.1，.clip 区间内）;
- **禁止**自由奔跑式迟同步（陈旧 >3 次更新触发仪表告警——新增断言）。

### 3.4 端口与基础设施扩展

- `portmap.SEGMENTS` 新增 `"fleet"` 段（建议 21000-21999，16 车道×10 宽 + learner 保留位），`rebuild_lane` 扩 slot 0-15; C12 断言+变异同步扩;
- boot 互斥锁（Local\th123_train_game_boot）天然串行化 16 实例的 boot 风暴: supervisor 以 20s 错峰拉起（启动期 ~5 分钟，可接受）; `_MATCH_FLAG` 降级模式在 16 实例下若触发会瘫吞吐——**健康标记 TTL 仪表化**，降级激活即告警;
- 游戏镜像: 云主机装好 th123_train + mod 集 + 血统校验（update_provenance 的 C9 断言在云机上同样可跑——**部署≠构建纪律自动延伸**）。

### 3.5 supervisor（fleet 版 run_parallel）

- actor/learner 死亡重启（沿用 30s 冷却+存活衰减+退出码语义 0/130/1）;
- **league 分配器**: 每 actor 的角色分配按 league 权重周期性重算（3 现役保底各 2-3 actor，余量给新角色/剥削位）; league 常量重标定（§7）;
- 停机卫生: Ctrl-C 先停 actor 再 join learner 最后 save（现行 KeyboardInterrupt 竞态修复的延伸）。

## 4. 数据流与容量

| 项 | 数值 | 说明 |
|---|---|---|
| 单局经验体积 | ~17MB（14.4KB 视觉 + ~2.5KB 侧向量 × ~1000 决策） | 含 logp/掩码后 ~20MB |
| 队列流量 | 600 局/h × 20MB ≈ **12GB/h** | 云 NVMe 落盘队列无压力; learner 消费滞后告警（队列 >5 局） |
| 快照体积 | ~2.3MB/版本 × 每 1-2 分钟一版 | 保留最近 3 版滚动 |
| GPU 更新耗时 | 4-8k 样本批 ~2-5s（A10） | ~100-150 更新/h → learner 占空 ~15% |

## 5. 学习质量保障（红线→机制→验证）

| 红线 | 机制 | 验证（门禁+变异） |
|---|---|---|
| ① logp 采样时记录 | actor 存 logP(a); update 接受 stored logp_old | 行为断言: 篡改一批 stored logp → 更新结果必须变红 |
| ② 同步纪律 | 局边界快照 + K≤8 + 60s 超时 | 陈旧度仪表 + "迟同步>3 次更新"断言 |
| ③ 环境独立 | 每 actor 独立 rng/deck/对手，种子可回溯 | 同种子重放决策序列一致性测试 |
| （附）生态稳定 | league 先于大吞吐生效; 池常量按吞吐重标定 | matchup 汇总回归测试 |

**V1 明示的语义差异清单**（不隐藏）: replay 缓冲 fleet 首版关闭（攒批已提供样本复用经济性）; bc_extra 照常（BC 库只读共享）; ppo_gpu 的 bc_mask/expert-ret 近似维持现状并记录。

## 6. 参数初值

| 参数 | 初值 | 依据 |
|---|---|---|
| K（局/批） | 4（上限 8） | 4-8k 样本/批=PPO 文献健康区间; 陈旧度 ≤1-2 更新 |
| actor 数 | 8 起步 → 16 | 8 vCPU/阶段验证后扩 |
| 快照轮询 | 局边界同步读 version | 文件 stat 廉价 |
| league 周期 | 每小时重算分配 | suika 失衡在 6× 速度下 1/6 墙钟演化——必须前置于扩量 |
| 池快照频率 | 50 局→按墙钟 30min 等价重标定 | 保持"对手新鲜度/墙钟"恒定 |

## 7. 实施计划（四阶段）

**P0 前置修复（本地，~半天）**
- F1: `_restart_same_process` 双 deck（第十七轮 S1，两行）;
- F2: ppo_gpu save 的 v_path 写真实值头键（往返断裂实测在第十七轮——**fleet 的硬前提**）;
- F3: ppo_gpu.update 增 stored-logp_old 参数 + bc_mask 传递; 清 `_one_hot` 死变量/`_CONV_MAP` 双定义;
- F4: episode 循环抽取共享库（actor 与 train_tm 同源）;
- F5: portmap fleet 段 + C12 扩展断言+变异。

**P1 本地干跑（1 天）**: 2 actor × 1 learner（本机核数允许的话 4 actor）——验证协议端到端; **A/B 质量对照**: 同角色 fleet vs 现行 trainer 各跑 N 小时，比对 |KL|/熵/值损/matchup 轨迹一致性（验收: 无系统性偏移）。

**P2 上云（1-2 天）**: 镜像烘焙（Windows+游戏+mod+pyenv+torch，含血统校验）→ 8 actor 浸泡 24h → K/批参数调优; 成本护栏: 按量计费+闲时自动停机脚本。

**P3 扩量+league（1 周+）**: 16 actor、20 角色 league 分配、池常量重标定、剥削者位; `bench_ppo_update` 实测 numpy/GPU 更新对比入档。

## 8. 验收标准

1. 吞吐 ≥5× 基线（≥40 万决策/h）且零新增 IndexError/NameError;
2. 24h 浸泡: 零死亡循环、队列滞后 <5 局、陈旧度仪表 <2 更新;
3. A/B 对照: fleet 与单实例的 |KL|/熵/值损/胜率轨迹无可区分系统性偏移;
4. 模型格式往返: fleet 产物被现行 train_tm/side_driver/outer_loop 无改动加载;
5. 门禁: 本设计 §5 的全部断言入 contract_check 且配对变异全拦截。

## 9. 风险登记

| 风险 | 缓解 |
|---|---|
| 多进程竞态（新事故面） | 原子写/版本戳/单写者纪律沿用; P1 本地干跑先行 |
| boot 风暴/降级模式瘫fleet | 错峰拉起; 健康标记仪表化+告警 |
| 云 Windows/D3D 环境怪癖 | 镜像烘焙后跑全量门禁+一局冒烟再入队 |
| 生态失衡被加速（suika 型） | league 前置+池常量重标定（§6） |
| 成本失控 | 按量+自动停机+吞吐/成本仪表 |
| episode 循环抽取引入回归 | 共享库被现行 train_tm 同步引用（不是复制）——现行路径即回归测试 |

## 10. 本设计的"不变面"（明确列出防误改）

奖励结构与常数 · 宏库与掩码 · frame_events/R34 规则层（环境动力学语义）· 退火日程（按更新次数）· BC/oracle 数据管线 · 模型 npz 格式 · 门禁与血统治理（扩展不绕过）· R1-R11 红线（公平性边界与本地锁步不变）。
